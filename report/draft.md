# 밀리의서재 메인 영역 추천 시스템 설계

---

# 1. 추천 목표와 활용 데이터

데모: https://millie-rec-production.up.railway.app/#/ (쇼케이스 화면에서 바로 눌러볼 수 있다, 가동 감시 https://stats.uptimerobot.com/20M6QwPo7z)

## 1-1. 배경과 목표 [추천 목표]
메인의 역할은 다음에 읽을 책이 계속 나오는 경험이고, 밀리는 가입 시 7단계 취향 설정으로 그 출발 신호를 직접 받는다. 이 문서는 그 신호를 메인에서 어떻게, 얼마나 오래 살려 쓸지를 추천 목표로 정한다.

**추천 목표.** 사용자가 취향 설정에서 직접 알려준 선호를 cold-start(콜드 스타트: 데이터 없는 초기 상태)의 강한 prior(사전 정보)로 사용하되, 이를 영구적인 취향 label(라벨)로 고정하지 않는다. 이후 실제 독서 행동과 현재 세션의 의도가 축적되면 행동 신호의 비중을 높이고, 사용자가 취향 설정을 다시 수행하면 새로운 explicit preference state(명시 선호 상태)를 생성해 즉시 추천에 반영한다. 이 사용자 상태를 바탕으로 Candidate Retrieval → Ranking → Re-ranking → Page Composition을 수행하여 "클릭할 책"이 아니라 "실제로 읽기 시작할 책"을 메인에 노출한다.

## 1-2. 추천 목표, 기대 효과, 측정 지표 [추천 목표]

| 관점 | 목표 | 측정 지표 |
|---|---|---|
| 비즈니스 | 추천 경유 독서 경험 → 구독 유지 | 30일 리텐션, 월 갱신율 |
| 사용자 | 열어보기 전에 흥미 있는 책을 찾는다, **어려워서 덮는 경험을 막는다** | 독서 시작까지 탐색 시간, 초반 이탈률 |
| 기술 (North Star: 북극성 지표) | **QRS**: 추천 노출 후 T분/T페이지 이상 읽기 시작한 세션 비율. T는 임의 확정하지 않고 실로그 분포로 결정 | 메인 경유 QRS / 메인 노출 활성 세션 |

**CTR(Click-Through Rate: 클릭률)은 진단 지표이지 목적이 아니다.** 클릭 최적화는 낚시성 콘텐츠를 보상한다. 도서에서는 주제가 맞아 클릭했지만 너무 어려워 초반에 덮는 **난이도 미스매치**가 그 실패이고, 난이도는 분량이나 카테고리와 별개다.

**기대 효과**
1. 신규 사용자가 첫 화면부터 *이유가 보이는* 추천("『○○』을 좋아하셨다면")을 받아 첫 독서 시작까지 시간 단축
2. 취향 재설정이나 완독 직후처럼 의도가 분명한 순간에 즉시 반응하는 메인
3. 난이도 미스매치 이탈 감소 → QRS 개선, **신규 사용자 첫 완독 도달률** 개선 → 구독 유지

## 1-3. 활용 데이터: 취향 설정 7단계는 전부 다른 종류의 신호다 [활용 데이터]

| 신호 | 어떻게 쓰나 | 쓰지 않는 방법 (흔한 실수) |
|---|---|---|
| 독서 시간대(다중 선택) | 맥락 신호로 수집하고 전달(응답의 `context`), 다중 선택이라 원-핫이 아닌 다중 핫 벡터. 포맷×맥락 교차항은 학습형 랭커 몫 | ✗ "자기 전 = 에세이" 같은 장르 규칙 |
| 책 고르는 기준(다중 선택) | 순위화 피처 가중(작가, 출판사, 인기도, 화제성, 평점 친화도). "좋아하는 작가"를 고르면 작가 선택 단계가 열려 작가 선호가 명시 신호로 추가되고 작가 통로가 후보 생성에 붙는다 | ✗ 기준 하나를 사용자 유형으로 고정 |
| 관심 카테고리, 세부 카테고리 | 후보 생성 필터와 부스팅(광범위 → 세분화 사전 정보) | ✗ 카테고리 밖 후보를 전부 차단 |
| 책 5권 선택 | 유사 도서 검색의 출발점 + 앵커 | ✗ **미선택 책을 부정 신호로 사용**. 노출 위치 때문에 못 본 것일 뿐 |
| 연령대(밀리 도서 데이터의 성별, 연령 독자 분포) | 사용자 연령대와 책의 독자 분포를 맞춘 cold-start 약한 사전 정보, 이력이 쌓이면 비중 0 | ✗ 연령으로 장르를 고정 |
| 페르소나 | "오디세우스의 서가" 같은 추천 이유 표현 | ✗ 모델 입력 (원본 신호가 위에 있음) |

취향 설정 화면은 추천 데이터를 만드는 정책이면서 노출 편향을 낳는 자리다. **미선택 책은 negative가 아니다**. 노출 위치 때문에 못 본 것일 뿐이므로 모든 추천 노출에 `추천 ID, 모델 버전, 행 ID, 위치`를 남겨 **A/B 귀속과 노출 편향 보정**의 전제를 만든다.

# 2. 추천 구조: 전체 플로우

## 2-1. 4단계 파이프라인 (그림 1) [추천 구조]

```mermaid
flowchart TD
    U["사용자 상태 U_t = α×취향설정 + β×장기 행동 + γ×현재 세션<br/>가중치는 증거가 쌓일수록 변한다"] --> R
    subgraph R["① Retrieval (후보 생성): 4통로 병렬 → 수백 권"]
        direction LR
        R1["협업 필터링<br/>함께 읽힌 책"] ~~~ R2["앵커, 콘텐츠 유사<br/>온보딩 5권 → 이웃"] ~~~ R3["인기, 급상승<br/>fallback"] ~~~ R4["신간, 탐색<br/>롱테일 기회, 설계만"]
    end
    R --> K["② Ranking (순위화) → 수십 권<br/>P(유효 독서), 명시 선호 친화도, 취향 세부 분류 가점, 난이도 적합도"]
    K --> RR["③ Re-ranking (재순위화)<br/>다양성, 중복 제거, 노출 자격(제목, 표지, 성인 표지), 신규 사용자 난이도 가드"]
    RR --> P["④ Page Composition (페이지 구성)<br/>어떤 행을 어떤 순서로: '이어 읽기'(재개) ≠ '추천 발견'(탐색)"]
    P --> M["메인 화면<br/>이어 읽기 / 『○○』을 좋아하셨다면 / 완독하셨네요, 다음은 / 오디세우스의 서가 / 지금 뜨는 책"]
    M -.노출과 행동 로그.-> U
```

후보 생성은 정밀한 순위화가 비싸므로 먼저 좁히는 단계(Recall@K), 순위화는 목표 지표 QRS를 직접 최적화하는 유일한 단계(NDCG@K), 재순위화는 같은 장르 반복을 막고 신규 사용자를 규칙으로 보호하는 단계(ILD@K), 페이지 구성은 Top-K 리스트가 아니라 페이지를 만드는 단계(행 단위 QRS)다. **후보 생성과 순위화의 분리**, **페이지 구성의 별도 단계화**는 대형 추천 서비스가 공개한 표준 구조이고, 규모는 실측한 밀리 공개 카탈로그(약 9천 권)에 맞춰 Item-KNN(Item-based k-Nearest Neighbors: 함께 읽힌 책 기반 유사도) + 콘텐츠 유사도로 충분하다.

## 2-2. 사용자 상태: 시간에 따라 변하는 가중치 [활용 데이터, 추천 구조]

$$U_t = \alpha_t\,U_{\text{취향설정}} + \beta_t\,U_{\text{장기행동}} + \gamma_t\,U_{\text{세션}}, \quad \alpha+\beta+\gamma = 1$$

| 사용자 상태 | α 취향설정 | β 장기 행동 | γ 세션 | 메인이 보여주는 것 |
|---|---|---|---|---|
| 가입 직후 (독서 0회) | **높음** | 0 | 0 | 온보딩 5권의 이웃 + 카테고리 인기 |
| 독서 축적 (n회) | 감쇠 $\alpha_n = \alpha_0 e^{-n/\tau}$ | **상승** | 낮음 | 실제 읽은 책 기반 추천이 초기 설정을 대체 |
| 취향 재설정 직후 | **다시 높음** | 유지 | 0 | 새 선호 즉시 반영, **기존 기록은 삭제 안 함** |
| 완독 직후 / 집중 탐색 | 유지 | 유지 | **일시 상승** | "완독하셨네요, 다음은" / 지금 찾는 주제 |

가중치는 **그 사용자에 대해 쌓인 증거의 양과 최근성의 함수**로 정해진다. 감쇠 속도 τ는 단정하지 않고 오프라인 재현 평가와 A/B로 정한다. **취향 재설정 ≠ 프로필 초기화**. 재설정마다 스냅샷을 새로 만들고 기존 기록은 유지하며 Nearline으로 수 분 내 반영한다("방금 알려줬는데 반영 안 됨"이 최악의 UX).

**구현.** 파이프라인 4단계가 코드 폴더와 1:1이고 경계는 아키텍처 테스트가 강제한다.

# 3. 기술 스택과 시스템 아키텍처

## 3-1. 운영 3계층 (그림 2) [추천 구조]

```mermaid
flowchart LR
    subgraph OFF["Offline (오프라인): 일 1회 배치"]
        O1["도서 임베딩, 이웃 행렬<br/>인기도 집계<br/>난이도(완독지수 잔차), 모델 학습"]
    end
    subgraph NEAR["Nearline (준실시간): 분 단위, 이벤트 도착 시 즉시"]
        N1["최근 행동 반영, 장기 프로파일 갱신<br/>취향 재설정 스냅샷 즉시 반영<br/>완독 직후 행 사전 계산, 캐시 무효화"]
    end
    subgraph ON["Online (실시간): 요청 시 p95 ≤ 200ms"]
        O2["피처 조회 30ms → 후보 병합 50ms<br/>→ 경량 순위화 60ms → 재순위, 구성 20ms"]
    end
    O1 -->|"아티팩트<br/>이웃, 벡터, 인기"| ST[("피처, 이웃 저장소")]
    N1 -->|"세션 상태<br/>스냅샷"| ST
    ST --> O2
    APP["밀리 앱 메인"] -->|"GET /recommend"| O2
    O2 -->|"200 OK"| APP
    O2 -->|"예산 초과, 예외"| FB["Fallback 단계적 대체<br/>0 개인화 → 1 캐시 → 2 카테고리 인기 → 3 전역 인기"]
    FB -->|"항상 200"| APP
    APP -->|"이벤트 로그"| N1
```

**요청마다 무거운 계산을 다시 하지 않는다**. 지연 예산을 기준으로 계층을 나눴고 추천 API p95 200ms(과제용 제안 SLO(Service Level Objective: 서비스 수준 목표); 내부 값 비공개)를 단계별로 쪼개 예산을 넘는 연산은 전부 Offline/Nearline으로 내렸다. 예산을 넘거나 예외가 나면 fallback cascade(단계적 대체) 0→3으로 내려간다.

**추천 API 장애가 메인 장애가 되어선 안 된다.** 파이프라인이 예외를 던져도 200 + 인기 행을 반환하는 것이 테스트로 존재한다(`tests/serving/test_smoke.py`의 fallback 200 테스트).

## 3-2. 기술 스택과 선택 이유 [추천 구조]

| 목적 | MVP (구현) | 실서비스 확장 | 이 선택의 이유 |
|---|---|---|---|
| 협업 필터링 | **Item-KNN** (scipy sparse cosine) | Two-Tower(투 타워: 사용자/아이템 임베딩 분리 학습) + ANN(Approximate Nearest Neighbor: 근사 최근접 탐색) 인덱스 | 실측 약 9천 권(공개 도서 페이지 9,447권, `results/millie_coverage.csv`) 규모엔 KNN으로 충분. **같은 이웃 행렬이 "『○○』을 좋아하셨다면" 행의 근거** |
| 콘텐츠 유사 | TF-IDF(Term Frequency–Inverse Document Frequency: 단어 빈도 기반 텍스트 벡터) + cosine | 텍스트 임베딩 모델 | 신규 도서, 신규 사용자 cold-start 통로 |
| 순위화 | 가중합(α β γ) | 다중 목표 학습형 랭커(유효 독서, 서재 담기, 완독 동시 예측) | 첫 모델은 단순하게: 파이프라인, 지표, 인프라를 먼저 검증한다(Google ML 설계 원칙) |
| 재순위화 | MMR(Maximal Marginal Relevance: 관련성과 다양성 균형) + 규칙 가드 | 학습형 re-ranker | 모델보다 규칙이 안전 |
| 서빙, 저장, 배포 | FastAPI + pydantic, SQLite(WAL), Docker 1컨테이너, Sentry, 5분 헬스체크 | Kubernetes, Feature Store + Redis, Prometheus → Grafana | 응답 형태를 코드로 고정, 스냅샷과 이벤트 영구 저장, 이미지와 헬스체크 경계가 로컬과 배포에서 동일 |

**의도적으로 넣지 않은 것.** LLM(Large Language Model: 대규모 언어 모델)은 넣지 않았다. 추천이 이 문제의 본질이고 LLM은 도서 소개 임베딩 같은 오프라인 표현 생성에만 쓸 여지가 있다. Two-Tower는 넣지 않았다: 약 9천 권 규모에서 Item-KNN 대비 이득이 작고 같은 이웃 행렬이 추천 이유(『○○』을 좋아하셨다면)까지 설명하는 장점을 잃는다. ALS(Alternating Least Squares: 행렬 분해 협업 필터링)도 설명력 차이가 작아 뺐다.

데모는 Kafka를 SQLite `events` 테이블 + 소비 루프로, 스트리밍 Nearline을 단일 프로세스 비동기 루프로, Redis 캐시를 프로세스 내 dict로 축소했고, 요청 경로 밖 갱신과 재계산 안 함이라는 경계는 같다.
각주: 데모 카탈로그는 밀리 공개 도서 페이지 9,447권(수치, 메타, 표지 URL만 저장, 리뷰 텍스트 미저장)이고 완독지수 커버리지는 82.5%다(`results/millie_coverage.csv`). 앵커 이웃은 제목/소개 TF-IDF cosine이고 동일 카테고리 비율은 0.356이다(`results/millie_edges_gate.json`).

# 4. 성능 평가 방법

## 4-1. Offline: 지표 3개가 구조 3단계와 1:1 (그림 3) [성능 평가]

```mermaid
flowchart LR
    A["① Retrieval<br/>후보 생성"] -->|"실제 읽은 책을<br/>후보에서 놓치지 않았나"| M1["Recall@20"]
    B["② Ranking<br/>순위화"] -->|"좋은 책을<br/>위에 올렸나"| M2["NDCG@10<br/>(Normalized Discounted Cumulative Gain:<br/>순위 가중 정답 점수)"]
    C["③ Re-ranking<br/>재순위화"] -->|"한 취향에<br/>몰리지 않았나"| M3["ILD@10<br/>(Intra-List Diversity:<br/>목록 내 다양성)"]
    M1 & M2 & M3 -->|"오프라인에서 거른 후보만"| AB["Online A/B 테스트<br/>Primary = QRS"]
```

지표가 단계와 1:1이므로 **어느 단계가 문제인지** 바로 읽을 수 있다.

**실측 (`results/latest_states.csv`, Goodbooks-10k, holdout, seed 42)**

## 4-2. Online: A/B 테스트가 최종 판정 [성능 평가]

**Primary**는 QRS/활성 사용자 하나로 출시 여부를 결정한다. Secondary(추천 CTR, 서재 담기, 뷰어 열기, 독서 시간, 완독, 신규 사용자 첫 완독 도달률)는 인과 사슬 확인, Discovery(카탈로그 커버리지, 장르/작가 다양성)는 인기 편중 감시, **Guardrail(안전장치)**(p95 지연, 오류율, fallback 비율, 중복 노출률, 구독 해지율)은 하나라도 악화되면 출시 보류다.

- 배정 단위는 **사용자 키**(기기 단위 배정의 폰과 태블릿 불일치 방지), 신규/기존 **층화**(취향 설정 효과는 신규에서 봐야 함), MDE(Minimum Detectable Effect: 최소 검출 효과) 기반 표본 산정
- 판정 규칙: `CTR↑ 그러나 QRS↓ → 실패` / `CTR≈ QRS↑ → 성공` / `QRS↑ 지연 폭증 → 배포 보류`

## 5-2. ★ 도서 도메인 고유 설계 3가지 [추천 목표, 활용 데이터, 추천 구조]

> ★ **앵커: "아는 책"으로 판단하게 한다.** 모르는 책은 설명을 읽어도 감이 안 오지만, 온보딩 5권은 사용자가 이미 아는 책이다. 그래서 첫날부터 "『○○』을 좋아하셨다면" 행을 만들고, 취향을 재설정하면 새 5권이 즉시 앵커가 된다(데모 캡처 ②와 ⑥, 본인 5권 앵커 사례 표). 향후 앵커는 완독한 책 → 서재에 담은 책 → 취향이 비슷한 다독가의 고평점 책으로 넓히고, 어느 앵커가 효과적인지는 bandit(밴딧: 실험하며 학습)으로 고른다.

> ★ **난이도: 밀리 완독지수에서 파생한다.** 밀리가 책마다 보여주는 완독지수(완독 확률, 예상 시간, 분야 평균)를 추천 피처로 되먹이므로 새 파이프라인이 필요 없다. 완독 확률을 그대로 쓰면 길이와 장르에 교란되므로 분야와 길이를 걷어낸 잔차로 난이도를 정의하고 사용자 수준과의 차이(gap)를 순위화 피처로 쓴다. IRT(Item Response Theory: 문항반응이론)가 말하듯 난이도와 능력의 차이가 결과를 좌우한다. 완독 확률의 분야 평균은 오디오북 40.3%에서 어린이 79.0%까지 벌어지지만 잔차 난이도의 분야 평균은 0.488~0.505에 모인다(8개 분야, 7,796권, `results/millie_difficulty.json`). 피처는 원시 완독지수 → 분야와 길이 잔차 → 사용자 수준 gap → 신규 가드(완독 3권 미만이면 잔차 하위 책을 첫 화면 상단에서 제외)의 4층으로 쓰고, 완독지수가 있는 책(82.5%)만 모집단이며 난이도는 UI에 숫자로 노출하지 않는다.

> ★ **시간 가변 가중치: 증거가 쌓일수록 취향 설정의 비중이 내려간다.** 사용자 상태는 취향 설정, 장기 행동, 세션 세 성분의 가중합이고, 가중치는 그 사용자에게 쌓인 증거의 양과 최근성의 함수다. 가입 직후엔 α=1로 온보딩 5권이 전부를 결정하고, 이력 n권이 쌓이면 α_n = max(0.2, 0.6×e^{−n/20})로 내려가며 나머지를 장기 행동과 세션이 나눈다. n≥20에서 NDCG@10이 pop 0.087 대 hybrid 0.240으로 격차 0.153이 난 것에서 이 설계가 숫자로 드러나고 같은 상태의 cf 0.237과의 차이는 작다.

## 5-4. 로드맵과 기억할 5가지 [추천 구조, 성능 평가]

**로드맵(설계만).** Two-Tower + ANN, 다중 목표 학습 랭커, Kafka 기반 Nearline, 텍스트 가독성 난이도, 다독가 리뷰 통로, Interleaving(인터리빙: 두 랭커 결과를 한 목록에 섞어 비교), 적응형 취향 질의(다음 질문을 불확실성 기준으로 선택).

**기억할 5가지.** ① 취향 설정 = 시작점이자 언제든 갱신되는 상태 ② 설문 7단계를 전부 다른 신호로 ③ 클릭이 목표가 아니다 ④ Top-K에서 끝내지 않고 페이지 구성까지가 메인 추천 ⑤ 정확도와 실서비스 제약을 같은 무게로 다룬다. 이 설계의 요지는 새 모델을 만든 것이 아니라 **검증된 추천 설계 원칙을 밀리의 UI, 데이터, 규모에 맞게 번역한 것**이다.
