# 데모 안내 — 버튼 다섯 개와 본인 5권 케이스

쇼케이스 첫 화면 "직접 눌러보기"의 버튼이 각각 무엇을 만드는지, 그리고 "본인 5권 정성 케이스"가
무엇이고 어디서 온 데이터인지 적는다. 면접에서 "이건 어떻게 만든 건가요"를 받을 자리라
동작을 코드 기준으로 정확히 남긴다.

배포 URL을 연 사람이 처음 보는 화면이 쇼케이스(`#/`)다. 폰 화면으로 들어간 뒤에는
**상단 제목 "밀리의서재 메인 추천 시스템 — 설계 데모"를 누르면** 언제든 이 화면으로 돌아온다.

---

## 1. 버튼 다섯 개

| 버튼 | 종류 | 하는 일 |
|---|---|---|
| **신규 유저로 체험하기** | 이동 | 취향 설정(`#/onboarding`)으로 간다. 7단계를 직접 밟는다 |
| **신규 유저 A** | 프리셋 | 취향 설정을 자동 완주한 뒤 메인으로 보낸다 |
| **건너뛰기 유저** | 프리셋 | 동의 없이 메인으로 보낸다 |
| **재설정 유저** | 프리셋 | 취향 설정 → 독서 2건 → 재설정까지 만든 뒤 메인으로 보낸다 |
| **관제 대시보드** | 이동 | 대시보드(`#/dashboard`)로 간다 |

이동 두 개는 화면만 바꾼다. 프리셋 세 개는 **상태를 실제로 만든다** — 서버에 요청을 보내고
스냅샷과 이벤트를 남긴다. 눌러 놓은 상태에서 인스펙터를 열면 그 요청의 결과가 그대로 보인다.

---

## 2. 프리셋은 어떻게 만들어지나

구현은 `demo/js/presets.js`다.

### 2-1. 세 프리셋의 공통 시작 — 깨끗한 상태

어떤 프리셋을 누르든 먼저 전부 지운다. `sessionStorage`의 mock 서버 상태와 이벤트 큐,
`localStorage`의 사용자 키를 지우고 **새 UUID를 발급한다.** 스냅샷 번호까지 1번부터
다시 시작한다. 앞서 누른 프리셋의 흔적이 남아 화면이 섞이는 일이 없도록 한 것이다.

### 2-2. 취향 설정 자동 완주가 하는 일

"신규 유저 A"와 "재설정 유저"가 공통으로 쓰는 절차다. **사람이 손으로 밟는 것과 같은 순서로
같은 이벤트를 남긴다.** 화면만 건너뛰고 로직을 우회하지 않는다.

1. `preference_started` 기록
2. 동의 `true`
3. 취향 값 채우기 — 독서 시간대, 카테고리, 책 고르는 기준, 세부 카테고리
4. `GET /api/candidates/onboarding` 으로 **후보 30권**을 받는다
5. 30권 **전부** `impression` 으로 기록한다. 위치와 `candidate_set_id`, `selected: false` 까지
6. 그중 **앞 5권**을 고른 것으로 처리하고 `preference_book_selected` 5건 기록
7. `POST /api/preferences` → 스냅샷 ID · A/B 셀 · 페르소나를 받는다
8. `preference_completed` 기록

5번이 중요하다. 고르지 않은 25권도 "보여줬으나 선택되지 않음"으로 남는다.
**미선택을 부정 신호로 쓰지 않되 노출은 전부 기록한다**는 설계(제출 문서 1-4)가
프리셋에서도 그대로 지켜진다.

카테고리 이름만 코드에 있고, 나머지 화면 텍스트는 전부 서버가 준 온보딩 메타에서 가져온다.
고른 카테고리가 지원 목록에 없으면 지원되는 첫 카테고리로 대체한다.

### 2-3. 신규 유저 A

카테고리 **IT · 소설 · 철학**으로 자동 완주한 뒤 메인으로 간다.

**볼 것** — 인스펙터의 가중치가 `α=1.0 · β=0 · γ=0`이다. 독서 이력이 없으니 취향 설정이
추천을 전부 결정한다는 뜻이고, 제출 문서 2-2의 첫 행이 화면에 그대로 나온 것이다.
메인에는 `『○○』을 좋아하셨다면` 앵커 행이 뜬다. 인스펙터에 A/B 셀 배정도 보인다.

관측된 행 구성: `anchor_2623` · `persona_shelf` · `trending` · `fresh_picks`

### 2-4. 건너뛰기 유저

**온보딩을 아예 돌지 않는다.** 동의를 `false`로 두고 메인으로 보낸다.

**볼 것** — 행이 두 개로 줄고(`trending` · `fresh_picks`) 상단에 "비개인화 인기 도서" 배너가
붙는다. 인스펙터의 모델 버전이 `fallback_v1`, fallback 단계가 3, 가중치는 전부 0이다.
개인 피처를 쓰지 않고도 메인이 비지 않는다는 것을 보여주는 화면이다.
동의 철회를 눌렀을 때 도달하는 상태와 같다.

관측된 행 구성: `trending` · `fresh_picks`

### 2-5. 재설정 유저

셋 중 가장 많은 일을 한다. 순서가 곧 설명이다.

1. 카테고리 **IT · 소설 · 철학**으로 완주 → 스냅샷 1
2. 추천을 한 번 받는다
3. `trending`이 아닌 행의 **앞 2권을 열어본 것으로 기록**한다(`reader_open` 2건)
4. `preference_restarted` 기록
5. 카테고리 **인문 · 역사 · 에세이/시**로 다시 완주 → 스냅샷 2

**볼 것** — 내 서재(`#/library`)에 스냅샷 타임라인이 **두 개** 쌓인다. 그리고 3번에서 만든
독서 기록이 **지워지지 않고 남아 있다.** 제출 문서 2-2의 "취향 재설정 ≠ 프로필 초기화"가
이 화면 하나로 증명된다. 메인의 앵커 행 시드도 새 5권으로 바뀐다.

관측된 행 구성: `anchor_621` · `persona_shelf` · `trending` · `fresh_picks`

## 3. 본인 5권 정성 케이스

### 3-1. 무엇인가

**설계자 본인이 실제로 읽은 다섯 권**을 취향 설정에 넣었을 때 시스템이 무엇을 추천하는지
보여주는 칸이다. 왼쪽이 넣은 5권, 오른쪽이 그 결과 상위 10권이다.

| 넣은 5권 | book_id |
|---|---|
| 싯다르타 | 1012 |
| 데미안 | 2765 |
| 위버멘쉬 | 1446 |
| 쇼펜하우어 인생수업 | 1222 |
| 빅터 프랭클의 죽음의 수용소에서 | 2292 |

Goodbooks 비교표가 "평균적으로 얼마나 맞히나"를 보여준다면, 이 칸은 **한 사람의 실제 취향에서
무엇이 나오는지**를 보여준다. 숫자로는 안 보이는 것을 눈으로 판단하게 하는 자리다.

### 3-2. 어떻게 만들어지나

`demo/scripts/make_mock.py`가 빌드할 때 계산한다.

1. 시드 5권 각각의 **콘텐츠 유사 이웃 상위 20권**을 가져온다
2. 다섯 묶음을 **번갈아 가며**(라운드로빈) 하나씩 뽑는다 — 한 권의 이웃이 결과를 독점하지 않게
3. 이미 나온 `book_id`와 **정규화한 제목**이 같으면 건너뛴다
4. 10권이 찰 때까지 반복한다
5. 각 권에 `『<어느 시드>』을 좋아하셨다면` 이라는 이유를 붙인다

**이웃은 협업 필터링이 아니다.** 제목과 소개의 문자 2~4gram TF-IDF 코사인이다.
밀리 공개 도서 페이지에는 사용자별 로그가 없어서 "함께 읽힌 책"을 계산할 수 없다.
화면 아래 캡션에 그렇게 적어 뒀다.

### 3-3. 서버가 계산하지 않는 이유

`GET /api/showcase`는 이 필드를 비워서 준다. 당연한 일이다 — **임의의 방문자에게
"본인이 읽은 5권"을 서버가 만들어 줄 수는 없다.** 특정 개인의 큐레이션이지 개인화 결과가 아니다.

그래서 화면이 빌드 시점 산출물(`demo/mock/showcase.json`)에서 이 칸만 채운다.
나머지 필드는 전부 서버 응답 그대로다. 같은 컨테이너 이미지 안의 파일이라
네트워크를 더 타지도 않는다.

### 3-4. 여기서 보이는 한계

『데미안』 2종, 『싯다르타』 3종처럼 **같은 작품의 다른 판본과 오디오북이 상단에 몰린다.**
제목·소개 TF-IDF로 이웃을 잡으니 당연한 결과다. 서빙 단계에서 동일 제목·저자를 묶는
판본 dedup으로 다루고 있고, 제출 문서 5-1에도 그대로 적었다.

면접에서 이 한계를 먼저 꺼내는 편이 낫다. 화면에 보이는 것을 설명 없이 두면
"못 걸렀네"로 읽히고, 먼저 말하면 "알고 있고 어디서 다루는지도 안다"로 읽힌다.

## 4. 화면 도는 순서

쇼케이스 아래 캡션에 적힌 동선이 그대로 추천 경로다.

```
취향 설정 → 메인 → 상세 → 뷰어(완독·별점) → 메인 "다음은" 행 → 서재(재설정·철회) → 대시보드
```

시간이 없으면 **재설정 유저 프리셋 하나만** 눌러도 된다. 스냅샷 두 개와 남아 있는 독서 기록이
한 화면에 있어서 설계의 핵심 주장을 가장 빠르게 보여준다.

인스펙터는 오른쪽에 항상 떠 있고, 지금 화면에서 어떤 신호가 어떻게 쓰였는지를 보여준다.
`?capture=1`을 붙이면 인스펙터와 상단바가 사라져 폰 화면만 남고, `?capture=2`는 인스펙터를
남긴다. PDF에 넣을 그림을 찍을 때 쓴다.

## 5. 나올 만한 질문

**"프리셋은 화면만 흉내 낸 건가요?"**
아니다. 서버에 실제로 요청을 보낸다. 후보 30권을 받아 오고, 노출 30건과 선택 5건을 기록하고,
스냅샷을 만든다. 사람이 손으로 밟는 것과 같은 순서로 같은 이벤트를 남긴다.

**"왜 후보 30권 중 앞 5권을 고르나요?"**
프리셋은 재현 가능해야 해서 무작위를 넣지 않았다. 사람이 직접 고르는 경로는
"신규 유저로 체험하기" 쪽에 그대로 있다.

**"건너뛰기 유저에서 행이 두 개뿐인데 버그 아닌가요?"**
의도한 결과다. 동의가 없으면 개인 피처를 쓰지 않는다. 개인화 행을 빼고
비개인화 인기 행만 남긴 것이고, 동의 철회를 눌렀을 때와 같은 상태다.

**"본인 5권은 왜 서버가 아니라 파일에서 오나요?"**
특정 개인의 큐레이션이라 서버가 방문자마다 만들어 줄 성질이 아니다.
빌드 시점에 카탈로그에서 계산해 파일로 굳혀 둔다.

**"이 추천 결과는 좋은가요?"**
정량 판단은 Goodbooks 비교표에서 하고, 이 칸은 정성 확인용이다.
두 트랙의 숫자를 섞지 않는 것이 이 프로젝트의 규칙이다.
